# Инструкции для работы с проектом

## Репозитории и ветки

- `origin` — личный форк: `https://github.com/pillboxru/mihomo-mikrotik.git`.
- `upstream` — репозиторий разработчика: `https://github.com/wiktorbgu/mihomo-mikrotik.git`.
- `master` — чистое зеркало `upstream/master`. Не добавлять сюда собственные коммиты.
- `personal` — личная рабочая версия: собственные workflow, README, настройки DNS и публикация Docker-образов. После перехода это ветка по умолчанию на GitHub.
- `feature/<тема>` — отдельное изменение для PR разработчику. Создавать от актуального `upstream/master`, а не от `personal`.

Личные изменения и изменения для разработчика оформлять отдельными коммитами. Этот `AGENTS.md` хранить в `personal` и не включать в PR разработчику или в зеркало `master`.

Запись этих инструкций не является командой выполнить переход, опубликовать образ или создать PR. Выполнять такие действия в рамках соответствующей задачи пользователя.

## Однократный переход на новую схему

Ветки уже разделены: `personal` опубликована и назначена веткой по умолчанию, `master` приведён к `upstream/master`. Не повторять переход. Порядок ниже сохранён как описание выполненной миграции.

1. Проверить рабочее дерево. Не терять и не перезаписывать незакоммиченные изменения. Перед операциями с GitHub проверить авторизацию `gh`.
2. Выполнить `git fetch origin` и `git fetch upstream`. Проверить открытые PR из `pillboxru:master` и зафиксировать текущий SHA `origin/master` для последующей проверки `--force-with-lease`.
3. Создать `personal` из текущего локального `master`. Сохранить все существующие доработки, включая два коммита DNS и настройку личных registry. Если в `origin/master` есть новые коммиты, включить их в `personal` через merge. Добавить этот `AGENTS.md` отдельным личным коммитом и опубликовать `personal` в `origin` с настройкой tracking.
4. Сделать `personal` веткой по умолчанию в настройках репозитория на GitHub. Запуски workflow по расписанию выполняются из ветки по умолчанию.
5. Проверить, что все личные коммиты доступны в `origin/personal`. Если есть открытые PR из старого `master`, сначала перенести предлагаемые изменения в отдельные тематические ветки и создать заменяющие PR со ссылками на прежние. Не менять основание существующих PR путём перезаписи их исходной ветки.
6. Находясь в `personal`, переставить локальный `master` на актуальный `upstream/master`. Однократно обновить `origin/master` с явно заданным ожидаемым SHA: `git push --force-with-lease=refs/heads/master:<сохранённый-SHA> origin master:master`. Это шаблон команды: заменить `<сохранённый-SHA>` фактическим значением из шага 2. При отказе проверки остановиться, проверить новые коммиты и сохранить их в `personal` до повторной попытки. Не использовать обычный `--force`.
7. Настроить локальный `master` на отслеживание `origin/master`, вернуться в `personal` и проверить ручную сборку.

Существующие изменения DNS сохранить в `personal`. Решение об отправке DNS PR отложено; не создавать его в рамках перехода.

## Получение обновлений разработчика

Перед началом убедиться, что рабочее дерево чистое. Обновлять `master` только через fast-forward:

```powershell
git fetch upstream
git switch master
git merge --ff-only upstream/master
git push origin master

git switch personal
git pull --ff-only origin personal
git merge master
git push origin personal
```

При ошибке любой команды остановиться и разобраться в причине до выполнения следующих команд. Если fast-forward для `master` невозможен, проверить отклонение от зеркала; не исправлять его автоматическим reset или force push.

При конфликтах merge в `personal` учитывать изменения разработчика и сохранять личное назначение workflow, настройки публикации и документацию. Не принимать целиком одну сторону конфликта без проверки. После разрешения конфликтов проверить результат и завершить merge перед push. Опубликованную историю `personal` обновлять через merge, без rebase и force push.

## Изменения для PR разработчику

Для каждой независимой доработки создавать отдельную ветку:

```powershell
git fetch upstream
git switch --no-track -c feature/my-change upstream/master
```

Заменить `my-change` названием задачи. Делать относящиеся к ней изменения и коммиты. Если доработка уже есть в `personal`, переносить только нужные коммиты через `cherry-pick`; проверять зависимости и итоговый diff. Не вливать `personal` целиком в тематическую ветку.

Документацию предлагаемой функции включать в её тематическую ветку. Личные адреса registry, оформление README и этот `AGENTS.md` оставлять в `personal`.

Перед публикацией проверить состав изменений и выполнить проверки, подходящие для доработки:

```powershell
git diff --check
git diff upstream/master...HEAD
git log --oneline upstream/master..HEAD
```

Публиковать ветку в `origin` и создавать PR в следующем направлении:

```text
pillboxru:feature/<тема> -> wiktorbgu:master
```

Чтобы использовать доработку до её принятия, можно влить тематическую ветку в `personal`. После принятия PR получить изменения разработчика обычным порядком синхронизации. Не переносить принятые изменения повторно через `cherry-pick`; при squash или rebase со стороны разработчика проверять возможные конфликты при merge.

## Сборка и проверки результата

- После перехода локальный `master`, `origin/master` и актуальный `upstream/master` должны указывать на один коммит. Все личные доработки должны быть доступны в `origin/personal`.
- Собственный workflow в `personal` должен публиковать образы в `ghcr.io/pillboxru/mihomo-mikrotik` и Docker Hub пользователя, заданного через `vars.DOCKERHUB_USERNAME`. Не заменять личные registry адресами разработчика при синхронизации.
- Для ручной сборки выбирать ветку `personal`. Проверять, что запись обработанной версии в `.github/versions` коммитится и отправляется в `personal`.
- Текущий workflow по расписанию собирает образ при изменении версии Mihomo. После изменения кода при прежней версии запускать сборку вручную.
- Перед PR проверять, что diff содержит только предлагаемые разработчику изменения.
- Эти правила не отменяют ограничения пользователя на чтение и поиск в каталогах Synology: работать только в разрешённой папке проекта и других явно указанных пользователем местах.
